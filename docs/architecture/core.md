# Architecture: Model, engine and automation

Part of the architecture notes indexed in [AGENTS.md](../../AGENTS.md). Keep each topic in its bullet here; AGENTS.md only lists the topics.

- **cc_core** — the BIM model. `Project` (levels, materials, `types: BTreeMap<ElementTypeId, ElementType>`, `elements`, `views`) is the single source of truth. Every edit goes through `Document::edit` / `edit_merged`, which records a reversible `Transaction` (elements, views, types and project "settings" are tracked); continuous edits use `edit_merged` + `break_merge`. `Document::start_journal`/`take_journal` note, while on, each element's state before the first change (edits, undos, redos and `discard_since` feed it from their `Transaction`s, one clone per element touched) and return the net `ElementChanges { added, modified, removed, other }` (compared with `PartialEq`; `other`: views, types or settings changed); `discard_since(depth)` undoes and drops steps that cannot be redone; `history_mark()` and `fold_since(mark)` fold later steps into the step that was on top, keeping its name and merge key. `Uid` is a persistent 128-bit id on project/types/elements (used as IFC GlobalId); `Document::new`, `from_ron` and `add_element/add_type` assign missing or duplicated ones. Files are versioned RON (`persist.rs`, `FORMAT_VERSION`): new fields must have serde defaults so older files load; bump the version for semantic changes. Old projects get missing ids and default annotation types on load.
- **Components** — `cc_core::component`: a `TypeData::Component { component, def }` holds a `ComponentDef` (params + pieces); types sharing `component` share the definition and differ in parameter values (the editor applies changes to all of them). Piece fields are `cc_core::expr` expressions (bounded parser, errors as values), except fixed `ComponentShape::Mesh` pieces (imported geometry); a sketched piece's `ProfilePoint`s run straight, along an arc (`radius`) or along part of an ellipse (`ellipse`) to the next point, and `cc_core::profile::from_curves`/`to_curves` turn sketch curves into these vertices and back; `ComponentDef::resolve` returns prisms (mesh pieces also carry their faces) in the component frame plus per-piece errors, and `cc_geom::component_parts` places them in the world (plans draw mesh pieces with `cc_geom::mesh_plan`). `.ccomp` files (`component_file.rs`) are validated on load. A `ComponentShape::Script` piece is Lua whose `geometry(p)` returns other pieces (`cc_core::component_script`: `ScriptEval`, hotspots, limits; `cc_script::object`: declarations, builders, `ScriptCache` and `shared()`, `sync`); its declarations are copied into `ComponentDef::params` (`from_script`; text, boolean, choice and material kinds, booleans stored as 1/0) and `hotspots`, elements keep `text_overrides` and moved `hotspots`, `ComponentDef::resolve_with` takes them in a `ResolveCtx`, and `cc_geom::resolve_instance`/`resolve_pieces` run scripts through the shared cache (a failing script keeps each element's last pieces); commands in `cc_engine::commands::component_script`. Doors and windows are components too (`cc_core::openings`): a `ComponentKind::Door`/`Window` definition with a `HostOpening` (width, height and default sill as expressions; `own_symbol` to draw its in-plan pieces instead of the category's swing or sash lines, `plan_only` pieces being 2D symbols with no solid) makes types of the door or window category, whose `ElementKind::Door/Window(Hosted)` elements cut that opening in their wall; the pieces are resolved with `WallThickness` defined, in a frame centered on the opening (x along the wall, y towards the side the door opens to, z up from the sill), mirrored by the element's flips (`cc_geom::opening_parts`, `ModelGeometry::opening_fills`). a window's `HostOpening::operation` (`cc_core::WindowOperation`: fixed, side-hung left or right, double, top-hung, horizontal or vertical pivot, sliding; `hinges` for plan swings (dashed arcs, `Drawing2D::dashed_arc`), `elevation_lines` for the elevation symbol that doors share, `ifc_panels`/`ifc_partitioning` for IFC export, `from_ifc_panels` for import; `openings::operable_window_def`, `OpeningNames::window_for`) sets its plan symbol; `ModelGeometry::opening_symbols` holds the elevation symbols of doors and windows as unfilled outlines just off both wall faces, which `projected::render` orders with the faces so what stands in front hides them, and plans dash a window wholly above the cut; a door's `HostOpening::door_operation` (`cc_core::DoorOperation`: one leaf hinged left or right, or a double door; `hinges` and `elevation_lines` as a window's, `ifc_operation`/`from_ifc` the IFC operation type, `ifc_panels` the `IfcDoorPanelProperties`) draws a swing per leaf, and `openings::operable_door_def`/`french_door_def` (glazed leaves over a `bottom_rail` parameter, `OpeningNames::door_for`) are the built-in ones, made by `door_type_create` (`cc_engine::commands::doors`); `ElementType::opening_size`/`default_sill`/`window_operation`/`door_operation` read either kind; the template's and IFC-imported door and window types are built-in definitions, and older files' fixed `TypeData::Door/Window` types become them on load (format 12).
- **Component reference planes and dimensions** — `cc_core::component_ref`: `RefPlane`s (expressions, origin planes `CenterX`/`CenterY`/`Base`), `RefDimension`s (`label`: a parameter writes the moving plane `from ± label`; `locked` (#499): `from ± distance`, serde default, so it follows `from`) and `RefEqual`s (EQ; `equal_holds` checks the middle is numerically halfway, whichever plane is written to keep it). Commands in `cc_engine::commands::component`: `component_dimension_add`/`_set` take `locked` (`lock` refuses a moving plane another expression sets; unlocking or deleting writes the plane as a number; `set_distance` keeps a locked one locked); `component_equal_add` tries `equal_candidates` in order (middle `(a + b) / 2`; else, when the middle is an origin plane or a labeled/locked dimension's `to`, the `from` plane of a dimension spanning `a`–`b` at `middle ∓ label / 2`; else an outer plane `2 * middle - other`) and keeps the first that holds with no new `ref_problems`, refusing with `msg-comp-equal-fixed`. The app (`cc_app::component_env`): `Env::scale` (options bar, `SCALES`, `view_scale`) sizes texts and dimensions; `cc_views::ViewDimension` carries the dimension `line`, `text_width`/`text_height` and `locked`, and `ViewDimension::distance_to` picks a dimension or EQ anywhere on its line or text (`dimension_at`, `equal_at`, hover-highlighted in Select); the picked unlabeled dimension shows a padlock (`dim_edit::paint_padlock`, `padlock_rect`) that toggles the lock, as does *Locked* in its properties; `equal_order` sorts the three picked planes so they can be clicked in any order.
- **cc_engine** — the engine: a `Session` (the `Document` plus cached geometry, drawings and sheets) and a catalog of commands (`registry.rs`). A command is a parameter struct (`Deserialize` + `schemars::JsonSchema`; its doc comment is the description, its fields' doc comments the parameter docs) implementing `Command { NAME, KIND, run }`; register it in `registry!`. Names are `snake_case` (valid MCP/model tool names). Edits go through `commands::edit`, i.e. `Document::try_edit` + a repair check, so a command that would leave the model invalid is refused without an undo step. Levels, types, views and materials resolve by id or name (`refs.rs`); lengths in meters, angles in degrees, points `[x, y]`. `*_get` queries show the `params` that `*_set` commands merge (JSON merge patch over the model's serde form). Errors are values (`EngineError { code, message }`); `Session::execute` guards panics. File access (`files.rs`): `Session::with_files(FileAccess, f)` narrows the files the commands running may touch (`FileAccess::All`, `None`, or `Granted(Grants)`, read and write path sets keyed by `files::read_key` (canonical path) and `write_key` (canonical folder plus file name); `narrow` intersects, so access is never widened), and every command that reads or writes a path checks it with `Session::require_read`/`require_write` (imports, `READS_FILES` commands, graph and macro files, and the exports); a `File` command runs under `Granted` only when it declares `Command::CHECKS_PATHS` (`registry::checks_paths`: `ifc_export`, `sheet_export`, `view_export`, `schedule_export_csv`, `analytical_export`, `fill_pattern_export`, `pipe_series_export`, `view_render`, `component_save`), and never under `None`. `Session::with_plugin_scope(PluginScope { plugin, edits: ScopeEdits, files }, f)` pushes the scope of a running plugin command (nesting-safe; scopes and file access are restored by `restoring` on every exit, also a panic); `Session::refusal`, called by `execute` for every command, refuses inside any scope `project_new`/`project_open`/`undo`/`redo`/`language_set`, `plugin_data_*` whose `plugin` is not the scope's, and edits unless `ScopeEdits::All` (`OwnData` lets only `plugin_data_set` through, `None` nothing), so graphs, scripts and macros a plugin starts are held to the same rules. Events (`extension.rs`: `Event::{ProjectOpened { path, new }, ProjectSaving { path }, ProjectSaved { path }, ModelChanged(ModelChange)}`, `EventKind`, `Event::payload`, `MAX_EVENT_IDS` = 10 000 per list with `truncated`): `Session::execute` fires them itself for top-level commands only (`top_level`: no nesting, no scope, not `firing`), through `Session::fire` (extension taken out, nesting bumped so what handlers run is neither top-level nor recorded, panics caught) and only when `Extension::listens(kind)`: `ProjectSaving` before `project_save` runs (path from the args or the document), then after success `ProjectOpened` when `Session::replace` ran (`replaced`; `new` = no path), `ProjectSaved`, or `ModelChanged` from the document journal, started only when the extension listens to it; `set_extension(Some)` fires `ProjectOpened` for the project held. `Session::with_event_scope(event, plugin, name, f)` runs handlers in `PluginScope { edits: OwnData (None after undo/redo), files: None }`; after `model_changed` of a command that left its own step on top (`fold_events`, from the history's depth and `undo_top_id` before and after it) their edits join that step (`Document::history_mark`/`fold_since`, which keeps the step's name and merge key, so a dragged value keeps merging and a macro step stays one undo step), otherwise they are squashed into one step `tx-plugin-event`. `Session::set_extension_quietly` moves plugins without `project_opened` (`AppState::close_document`, the app's Close). Pending jobs (a plugin command waiting for an external program): `Extension::start` (default: `run`) may return `Outcome::Pending`; `execute` notes what it needs to finish the command (`Begun`: name, top-level, journal, undo depth and top, merge key, recorded args, first id) in `PendingJob`, and `finish` does the rest when it ends (squash into one step, or `undo_to` on failure and `discard_since` when `Cancelled`, record, `fire_after`). A blocking session (the default; `set_blocking`, `with_blocking`) waits in `wait_job` (`drive_job` with `WAIT_STEP` 100 ms); a non-blocking one (the app) returns `ErrorCode::Pending` when the command is top-level (commands run by other commands, and `script` steps through `with_blocking(true)`, always wait). `poll_job` (`drive_job(0)`: extension taken out, nesting bumped, `Extension::resume`, panics guarded and followed by `Extension::cancel`) gives the result once; `cancel_job` calls `Extension::cancel` and fails it with `ErrorCode::Cancelled`; `job()` is a `Job { command, info: JobInfo { plugin, plugin_name, tool, last_line }, elapsed }`. While `job` is set, `refusal` lets only queries run (no other extension command), `top_level` is false (no events, no journal restart), and `set_extension`, `set_extension_quietly` and `replace` cancel it first; the blocking mode survives `replace`. Creation defaults shared with the drawing tools live in `defaults.rs`; localization (`i18n.rs`, the `t!` macro) lives here too and `cc_app::i18n` re-exports it.
- **Plugin data** — `cc_core::plugin_data`: `Element::plugin_data` and `Project::plugin_data` (`PluginData`, plugin id → JSON text; the project's is tracked as settings, `EditCtx::plugin_data_mut`) keep what plugins store, like attribute dictionaries. Values are compact JSON *text*, so the RON file never holds a free-form value tree; `valid_plugin_id` (shared with `cc_plugins::plugin::valid_id`), `MAX_PLUGIN_DATA_BYTES` (256 KiB per entry), `MAX_PLUGIN_DATA_DEPTH` (64, checked by `nesting` without parsing) and `repair` (drops bad ids, text that is not one JSON value or is `null`, and entries over either limit) guard it; copies of elements keep it (format 33). Commands in `cc_engine::commands::plugin_data` (group "Plugin data"): `plugin_data_get` (`null` when none), `plugin_data_set` (one undo step; `data: null` removes) and `plugin_data_list` (`{ project, elements }`); any caller may name any plugin id, except plugin commands, whose `PluginScope` limits them (and whatever they run, graphs included) to their own id (`ccad.data`).
- **Measurement systems** — `cc_core::MeasurementSystem` (metric, imperial) is not stored: a project is imperial when its length unit is (`Units::system`, `Project::measurement_system`); `Units::imperial()` (feet and inches to 1/16", ft², ft³, `SlopeUnit::RisePer12`, format 28) is the imperial template's and the Units dialog's preset. `project_new { template }` and `Project::from_template_system` build either template from the same code, reading what differs from `cc_core::template_spec` (`TemplateSpec`: sizes and `tpl-imp-*` name keys, the stair and dimension style rules, library sizes rounded by `units::round_imperial`; `concrete_walls`, the reinforced concrete wall types: one Structure layer of the template's concrete and `structural: true`, added last by `add_template_concrete_walls` and shown in the legend, not added to older projects on load), and `cc_core::Defaults` (`Project::defaults`) holds what commands and tools give things made outside the template per system (story and ceiling heights, the ramp, baseboard, tray, conductor, door, curtain and device sizes, pipe and device elevations, drain falls, rebar, terrain), so on-demand types get round imperial sizes and `tpl-imp-*` names. `cc_core::scale` writes and reads `1/4" = 1'-0"` scales; `SheetSize` has the ANSI and ARCH sizes. Display goes through `cc_views::format` (thread-current units, set by `Session::execute`/`sync` and `AppState::sync`, with `_with` twins): `length`/`meters`/`parse_length`, `size` (small sizes: the metric form each place always had, `MetricSize`, or inches without feet, `inch_size`, `parse_size` reading a bare number as inches), `area`, `volume`, `slope`/`parse_slope` (`6:12`), `bar_diameter`/`bar_size` (bar tags, the bending schedule and the `Diameter` field of bars, with a decimal point when `Units::diameter_point` is set, #437), `scale`, `paper`/`paper_weight`/`parse_paper` (sizes on paper, stored in mm), and `quantity` (`Quantity`: kg/lb, kg/m and lb/ft, kg/m² and lb/ft², kg/m³ and lb/ft³, MPa and ksi, l/s and gpm). `i18n::set_language` selects the decimal separator and Russian unit symbols in `cc_views::format`. Length and paper-size parsers accept Latin and Cyrillic suffixes. Schedule headers come from `ScheduleField::key_in(system)` (`col-imp-*`, no unit), schedule `Value::Size` cells read in inches, check messages have `*-imp-*` twins; the app uses `properties::length_drag`, `size_drag`, `slope_drag`, `paper_drag`, `field_label`, rounds free points with `tools::round_step` (1/2" to 20'-0" in imperial) and `AppState::follow_system` moves tool sizes still at one system's default to the other's. Engine parameters and results, files, IFC and DXF stay SI; expressions keep their stored units; conductor cross-sections stay mm²; the metric output is pinned by `tests/imperial_text.rs`, which also scans an imperial project for metric units.
- **Visual programming graphs** — `cc_engine::graph`: a `Graph` (`.ccgraph`, JSON, `GRAPH_FORMAT`; `from_json` bounds sizes, drops dangling, repeated and cycle-closing wires) of `Node`s (`NodeKind::Command` — every catalog command, ports from its JSON schema through `ports::type_of_schema`, plus `element` for `*_create`; `Builtin` — `builtin::catalog`, pure, query or edit functions over JSON values; `Lua` — a pure function in the `cc_script` sandbox, no model access) joined by `Wire`s. `eval::Evaluator::run` runs them in `Graph::order` (dependencies first, then lowest id), maps lists over ports (`lace`: a value deeper than the port's `rank` runs once per item; shortest, longest, cross; `MAX_CALLS`), squashes the run into one undo step and caches outputs while the document revision is unchanged. Elements an edit command creates are bound in `Project::graph_bindings` (`cc_core::graph_binding`: graph uid, node, lacing path, index; tracked as settings, dropped with the element and by repair): on the next run the element made by the same call takes the new content and keeps its id, uid, mark, comments and phases (`eval::bind`), and bound elements whose call no longer ran successfully are deleted; failed, skipped and cached nodes keep theirs. Commands in `cc_engine::commands::graph` (`graph_run`, `graph_check`, `graph_nodes`, `graph_elements`, `graph_release`); `ccad graph <file> key=value`; `examples/graphs/house.ccgraph` is run by a test.
- **cc_plugins** — Lua 5.4 scripts and plugins over the engine (`mlua`, vendored; no system Lua). `sandbox.rs`: a state with only `table`, `string`, `math`, `utf8`, `coroutine` and the base library minus `load`/`dofile`/`loadfile`/`require`/`collectgarbage`, an instruction budget per run (a global hook, so coroutines count) that `pcall`/`xpcall`/`coroutine.resume` re-raise, a memory limit and captured `print`. `convert.rs`: JSON ⇄ Lua (arrays carry the array metatable, whole floats become integers, depth and size bounded, cycles refused). `api.rs`: the `ccad` table (`run`, `try`, `commands`, `describe`, `null`, `array`, `json`); the session functions live only inside `Lua::scope` for a run, behind wrappers that stay, and what a plugin command may run is the engine's `PluginScope`, set by `Plugin::call` around the run (`Session::with_plugin_scope`), not checked on the Lua side; scripts are not restricted. A plugin's `Api` (`install_for_plugin`) also has `ccad.file.read/write` over a `FileRun` (the run's `Grants` plus the writes kept in memory: at most 64 MiB read per file, 256 MiB written per run; `FileRun::commit` writes each to a temporary file in its folder and renames them all into place, only after the command succeeded). `API_VERSION` is 3 (Plugin API 3 adds `permissions = ["network"]` with `allowed_hosts`, scoped HTTPS + per-plugin cache `ccad.http.{get,download,cached,read_cached}` in `http.rs` (allowlist checked on every redirect; SHA-256 checked when given), and `[[catalogs]]` Component Library providers registered via `ccad.catalog`). `script.rs`: `run_script` (`ccad lua`). `store.rs`: the community index (`index.json`, `IndexPlugin::best` picks the newest version for this build's plugin API and version) and checked installs from downloaded bytes (SHA-256 against the index, the zip read in memory by `cc_skp::zip` with bounded sizes, no unsafe paths or links, the plugin loaded from a staging folder before it replaces the installed one), `install_archive` and `uninstall` (which also drops the plugin's settings); stored setting values in `<plugins folder>/.settings/<id>.json` (`settings_path`, `read_settings`: at most 64 KiB, anything but a JSON object reads as empty, `write_settings`: temporary file renamed over); no networking. `plugin.rs`: `plugin.toml` manifests (id, api, main, `permissions = ["files"]`), `require` limited to the plugin folder, `ccad.command { name, title, description, kind, params, run }` collected while `main.lua` loads, `ccad.settings` (read-only proxy whose metatable `__index` the host refills before each command) and `ccad.data.get/set/list` (the plugin's own `plugin_data_*`), and `PluginHost`, the `cc_engine::Extension` that runs `<id>__<name>` commands; `ccad.on(event, fn)` (while `main.lua` loads only, then replaced by a function that raises; unknown names fail the load; `MAX_HANDLERS` 32) keeps `Handler`s, which `PluginHost::on_event` runs plugin by plugin in load order, each plugin's in one `Session::with_event_scope`, each call with `Sandbox::reset_budget_within(EVENT_INSTRUCTIONS = 50 M, EVENT_TIME = 5 s)`; a failing call becomes a message (`[id] <event> handler n: …`), its edits are dropped (`Document::discard_since`) and after `MAX_FAILURES` (3) in a row the handler is off; grants are the host's choice (`Plugin::grant`, only what the manifest asks). Plugin API 2 (`contributions.rs`, `locales.rs`; manifests with `api = 1` load unchanged and may not use these): `[[buttons]]` (`ButtonSpec` → `Button`: full command name, label, panel, canonical icon path checked inside the folder and ≤ 64 KiB, `ButtonSize`, `Vec<When>` with `When::{Selection, SelectionOne, SelectionOf(category), View(kind)}`; a button whose command is not registered fails the load), `[settings.<key>]` (`SettingSpec` → `Setting` with `validate`, kept in manifest order through `toml::Spanned`; `current_values` drops stored values that do not fit; `PluginHost::load_folder` reads the stored ones in a folder of plugins, a single plugin's folder gets the defaults; `PluginHost::set_setting` changes the live value; `settings_schema(dir)` reads them without running code, for `ccad plugins settings`), `locales/<code>.toml` (`Locales`: flattened keys; `%key%` text resolved at query time in `cc_engine::i18n::language()`: exact code, same base language, `en`, the key), and parameter UI hints checked at registration (`check_param_hints`: `ui` with its JSON type, `category`, `extensions` (with `save_path`/`open_path`; `path_params` lists a schema's path parameters), `enum_labels`, `title`). Scoped files: `Plugin::call` turns the top-level `save_path`/`open_path` arguments into `Grants` (`grants`: string, not empty, extension in `extensions` case-insensitively, resolvable; refused before running) and runs in `FileAccess::Granted` unless the plugin has `files` (then `All`). External programs (`tools.rs`, `process.rs`, api 2): `permissions = ["tools"]` (`Permissions::tools`) and `[[tools]]` (`ToolSpec`: id like a plugin id, name, 1 to 8 `executables` file names without folders and not `.bat`/`.cmd`, https `homepage`, `version_args`; at most `MAX_TOOLS` 8; refused without the permission or under api 1); `Plugin::tools()` (`Tool`, name resolved, `path` chosen, `problem`), `set_tool_paths` (stored, checked when used) and `set_tool_path` (`tools::check_path`: absolute, an existing file, its name one of `executables`, case-insensitive on Windows); `load_folder` reads `<folder>/.tools/<id>.json` (`read_tool_paths`: at most 64 KiB, a JSON object of tool id → absolute path, anything else left out; `write_tool_paths`: temporary file renamed over, none removes it; `uninstall` removes it); `tools_schema(dir, folder)` reads them without running code; `find_on_path` and `tools::test` (`version_args`, `TEST_TIMEOUT` 10 s). A command's `run` function runs in a coroutine (`Plugin::start` creates the `mlua::Thread`, `step` resumes it inside `with_plugin_scope` + `with_session` with a `CommandRun { files: FileRun, process: ProcessRun }`); `ccad.process.run` (PROCESS_PRELUDE) calls the scoped `process_run`, which checks the call (`prepare`: the current thread is the command's, the permission, the tool and its path, options `args`/`files`/`copy`/`outputs`/`timeout` only, names by `process::check_name`, a `copy` source among `FileRun`'s granted reads, inputs at most 256 MiB counted before anything is copied out of Lua, timeout 0 to 7200 s), stores the `Request` with a fresh token table and returns the token, which the prelude yields; `step` accepts only a yield of that token (by pointer) and starts `process::Running` (a background thread: `RunFolder` `constructcraft-<plugin>-<random>` created with `create_dir` and removed on drop, inputs written and copied, `Command` with `env_clear` plus `ENV_ALLOWED` and `LC_*`, null stdin, `CREATE_NO_WINDOW` on Windows, reader threads keeping 1 MiB per stream and the last line, `try_wait` every 20 ms, `Child::kill` on timeout or the cancel flag (also set on drop), readers given 2 s, outputs matched by `*` patterns per path part without following links, at most 64 MiB each and 256 MiB in all), leaving the command `Suspended` and reporting `Outcome::Pending`. `Plugin::resume` waits on it, gives the waited time back with `Sandbox::extend_time` (the instruction budget goes on), and resumes the coroutine with `finished_table` (`code`, `stdout`, `stderr`, `truncated`, `timed_out`, `files`) or `(nil, message)`, which the prelude raises; `cancel` stops the program and drops the coroutine and its `FileRun`. Event handlers get a `process_run` that raises, scripts have no `ccad.process`, and `main.lua` has none while it loads. `PluginHost` keeps the `pending` plugin id for `resume`/`cancel`/`job`, and its `run` drives `start`/`resume` to the end. The test program `cc_plugins_test_tool` (`src/bin/test_tool.rs`, steps such as `args`, `write`, `sleep`, `exit`) stands in for real tools in `tests/process.rs`. `[[exporters]]`/`[[importers]]` (`FileActionSpec`, at most 16 each, api 2) are checked after `main.lua` loads against their command (exactly one `save_path`/`open_path` parameter, `file_actions`) and listed resolved by `Plugin::exporters`/`importers` (`FileAction`: full command, label, param, extensions). Resolved text: `Plugin::display_name`/`display_description`/`commands`/`buttons`/`settings`, `PluginHost::command_title`, `summary` (commands with `title`, `buttons`, `settings` with `value`, `exporters`, `importers`, `tools` with `path` and `problem`). On the engine side `extension.rs` defines `Extension`; `Session::execute` takes it out while one of its commands runs (so plugin commands do not nest), squashes the command's undo steps into one (`Document::squash_since`) and undoes them on failure, and records only top-level commands in macros; `Session::commands`/`describe`/`kind_of` list both; `project_open` replaces the document with `Session::replace`, which keeps the extension.
- **Plugin development** — `docs/lua/ccad.d.lua` is the LuaLS `---@meta` file of the whole `ccad` table (classes `ccad`, `ccad.json`, `ccad.plugin`, `ccad.data`, `ccad.file`, `ccad.process` with `ProcessRequest`/`ProcessResult`, `ccad.test`, `ccad.CommandSpec`/`Params`/`Param` with the `ParamUi` alias, `ccad.EventName` and the event payload classes); `cc_plugins/tests/testing.rs` walks the runtime table of a plugin command and of a script with `ccad.test` and fails on a path not declared there (`function ccad.x(`, `ccad.x =`, and `---@field` lines under their `---@class`). `cc_plugins::testing`: `install_helpers` (the `HELPERS` Lua prelude: `ccad.test.eq` deep with cycles, `near`, `fails` plain substring then Lua pattern, `ok`, each `error(…, 2)`), `test_files` (`tests/*_test.lua`, sorted, at most 1000), `session_with_plugin` (`Session::default()`, the plugin's folder through `PluginHost::load_folder` granted `Manifest::requested`, the `--tool` paths), `run_tests` (manifest and tools checked first as usage errors; each file run once in a fresh session through `Api::install` + `with_session` with no scope, as `run_script`, which also lists its global `test_*` functions; then each function in a fresh session after the top level; output = the sandbox's prints plus `Session::take_extension_messages`).
- **cc_cli** — the `ccad` binary (no egui/wgpu): `commands`, `schema`, `reference`, `run` (JSON, `@file`, `-` or `key=value` arguments), `script` (JSON array or lines; stops at the first error), `lua` (a Lua script), `graph` (a `.ccgraph`, inputs as `key=value`), `plugins`, `mcp` (an in-house MCP server: JSON-RPC 2.0 over stdio, every command a tool with its schema; `mcp.rs`). Options `-p` (open `.ccad` or import `.ifc`), `--save`, `--save-as`, `--plugins` (repeatable; grants what manifests ask), `--tool <plugin>.<tool>=<path>` (repeatable; `PluginHost::set_tool_path` after loading, a bad one reported on stderr), `--lang`. `plugins new <folder> <id> [name=…]` (`scaffold.rs`: `scaffold::files` is the template, `create` refuses an invalid id, a bad name or an existing folder and removes what it made on failure; `scaffold::TYPES` embeds `docs/lua/ccad.d.lua` with `include_str!`) and `plugins test <plugin folder> [--filter t] [--tool …]` (`plugin_test` over `cc_plugins::testing::run_tests`: `PASS`/`FAIL` lines, the failed tests' output indented, a summary; exit 1 on a failure or no match, 2 on usage errors). `plugins tools <folder> <id> [tool=path …] [--test]` (`plugin_tools`) prints each tool (path, `problem`, a `find_on_path` suggestion, and with `--test` the `tools::test` answer), after checking and storing the given paths (`tool=` forgets one); sessions block, so plugin commands that run programs simply take their time. What plugins print goes to stderr.
- **Material libraries** — `cc_core::material_library`: a `MaterialLibrary` (format 1 JSON: `code`, `name`, `region` as a `pipe_catalog::Region` code, `standard`, `sources`, `materials`) of `LibraryMaterial`s (name, `MaterialClass`, color, description, physical values in SI units, all optional; `to_material` applies `template_properties` then the values, `of_material` the reverse), read by `read_library` (bounded by `MAX_FILE_BYTES`/`MAX_MATERIALS`, names distinct ignoring case, values finite and not negative, Poisson up to 0.5; errors name the row) and written by `write_library`. The built-in files are `assets/materials/*.json` registered in `BUILT_IN` (code, `material-library-<code>` name key, region), read once by `built_in()`, found by `find`; `BuiltIn::region` is `None` for an international library. The Brazilian ones (`BR-ACO-ESTRUTURAL`, `BR-ACO-ARMADURA`, `BR-CONCRETO`) keep market-language names and cite their standards, and a test checks the concretes' moduli against `concrete_modulus_nbr6118`; the international ones are by physical kind, with generic names, no trade names and ISO 10456 values only (`PAINTS`, `CERAMICS`, `STONES`, `MORTARS-PLASTERS`, `WOODS`, `GLASS`; a test checks that none cites a Brazilian standard), and the Brazilian finish libraries hold the NBR 15220-2 Table B.3 values, Brazilian wood species and stones (`BR-CERAMICAS`, `BR-PEDRAS`, `BR-ARGAMASSAS-GESSO`, `BR-MADEIRAS`, `BR-ISOLANTES`; a test checks the woods' and ceramics' density bands); a Brazilian row named after an international one ends in ` (NBR 15220-2)`, so both load into a project. A row's optional `finish` (`Finish`) sets the appearance's finish (`of_material` writes it unless matte). A row's optional `names` (language code → name, at most `MAX_NAMES`; `read_library` checks the codes and that names are distinct in each language) translates it: `name_in(lang)`, `all_names`, `to_material_in(lang)`; `MaterialLibrary::material` finds a row by its main name, then by a translated one. The built-in files carry names in the app's languages (a test checks the codes). `MaterialPhysical::yield_strength` (MPa, serde default) holds a steel's fy/fyk; `tensile_strength` its fu. Engine (`commands::materials`): `material_catalog` (the libraries, or one with its materials and `in_project`), `material_library_import` (`library`, `path` or `text`; `materials` by any of their names; named in `language`, default the active one; a material the project has under any of its names is `kept`; one undo step), `material_library_export` (project materials to a file, refused unless it reads back). App: `material_library_dialog.rs` (*Libraries…* in `material_browser.rs`; region filter (a region shows its libraries and the international ones), list, the selected library's table with checkboxes, a color swatch and only the value columns the library has (`COLUMNS`), *Load selected*/*Load all*, *Import File…*, *Export Materials…*; `graphics_dialog::Edits` so Cancel undoes).
